## Context

posttrainllm already has the factory stages, Swift/MLX SFT and PEFT commands, an ignored run-folder schema, eval/report tooling, and a package pattern. It does not have chess data or evaluation surfaces. More importantly, its current `posttrainllm sft --qlora` mode simulates quantization by quantizing and dequantizing the base in memory; the repo's QLoRA PRD identifies real packed-base loading and gradient flow as the prerequisite for honest 8B adaptation on this 48 GB Mac.

Chess is useful here because it turns language-model behavior into a verifiable state/action problem. Rules determine legality, Stockfish supplies a calibrated continuous move-quality signal, and paired games reveal compounding-error and recovery behavior. The stakeholders are the project owner as operator/learner and future consumers of a local routed chess specialist. There is no production or Pace consumer in this change.

## Goals / Non-Goals

**Goals:**

- Produce one reproducible Qwen3-8B baseline-to-candidate factory run with a clear ship/retry/reject decision.
- Teach standard-chess move selection from FEN/history to one UCI move.
- Measure legality, tactical skill, engine-relative move quality, game outcomes, general breadth, latency, RAM, throughput, and cost/time separately.
- Exercise real Mac-feasible 8B adapter training or document the precise packed-base blocker and use the best existing fallback.
- Preserve enough provenance to reproduce data, engine labels, training, evaluation, and packaging.

**Non-Goals:**

- Building a chess GUI, chess server, conversational coach, natural-language annotator, or replacement for Stockfish.
- Training a model from scratch, full-parameter tuning, distributed training, Chess960, chess variants, online play, or autonomous publication.
- Claiming grandmaster/Elo strength from puzzles or centipawn loss alone.
- Adding RL before the supervised baseline and its failures are measured.

## Decisions

### 1. Model output is one strict UCI action

Version 1 uses FEN plus recent UCI history as text input and exactly one UCI move as output. UCI is simpler and less context-sensitive than SAN, maps directly to a legal action, and is easy to validate. The evaluator does not salvage moves from prose because a deployed action policy must be parseable without a second model.

Alternatives considered:

- SAN: human-readable but requires contextual disambiguation and introduces avoidable parser errors.
- JSON: extensible but adds punctuation/schema tokens without benefiting a single-action policy.
- Free-form explanation plus move: useful for coaching, but reasoning quality and move quality become entangled and harder to score.

### 2. Use a rules library plus Stockfish; do not implement chess

A maintained chess library owns FEN/PGN parsing, legal move generation, state transitions, and UCI process integration. A pinned Stockfish binary supplies teacher labels and engine-relative evaluation. Both are development/eval tools, not production dependencies. Version and engine configuration are captured in manifests.

This follows the repo's adopt-first policy. Reimplementing chess legality, repetition, castling, en passant, promotion, checkmate, UCI transport, or search would create a second project and a less trustworthy ruler.

### 3. Freeze by position groups, not extracted rows

Raw games or generated trajectories are assigned to splits before position extraction. Canonical position hashes are then checked across splits and collisions are consolidated or removed. Clock fields are excluded from the canonical hash; piece placement, side to move, castling rights, and en-passant state remain. This reduces leakage from repeated openings and transpositions.

The pipeline emits distinct datasets:

1. `tiny-overfit`: 1–10 KB repeated examples covering ordinary and special moves.
2. `pilot-train`: a bounded stratified sample used to validate learnability and the harness.
3. `train`: approved human/engine-labelled behavior-cloning rows, created only if the pilot passes.
4. `dev`: recipe selection and failure analysis.
5. `test-offline`: frozen positions for legality, tactics, move quality, and slices.
6. `test-match-openings`: frozen paired openings, never used for training or prompt examples.

### 4. Mix expert imitation with recovery positions

Human/expert or strong-engine positions cover good-state behavior. Additional positions are generated by applying legal suboptimal moves, sampling weaker-engine play, or rolling out the current base, then asking Stockfish for a recovery move. This directly addresses behavioral cloning's compounding-error failure without starting with RL.

Sampling and weighting are frozen and reported. Engine scores are used for stratification and evaluation, not copied into the model prompt. Training targets remain legal UCI actions.

### 5. Baseline, SFT, then evidence-triggered optimization

The exact Qwen3-8B base is evaluated first. If it already clears the frozen bars, fine-tuning stops. Otherwise:

1. Prove packed-base adapter gradients with one bounded step or select the fallback.
2. Pass the tiny-overfit gate.
3. Run a small SFT/behavior-cloning pilot.
4. Evaluate on the complete offline suite and smoke match.
5. Scale SFT only after a positive pilot.
6. Add DPO/SimPO/ORPO or RLVR/GRPO only in a new recipe tied to a measured failure such as blunder selection, adverse-position recovery, or illegal formatting.

The initial recipe starts with LoRA rank 16 or 32 over attention projection layers, sequence length chosen from measured protocol token counts, and conservative optimizer settings derived from an existing working Qwen recipe. Exact values are frozen after the tiny-overfit check, not guessed into this design. A single configuration is preferred; any sweep needs separate approval and budget.

### 6. Real QLoRA is a hard truthfulness boundary

The preferred native path is packed 4-bit base loading, adapter injection after quantization, frozen base parameters, and gradients only through LoRA/DoRA parameters. Its bounded feasibility gate checks logits/load parity, adapter gradients, finite loss, unchanged base weights, adapter save/load, and RSS.

If MLX-Swift cannot pass that gate, use pinned Python `mlx_lm` for training and keep Swift/posttrainllm for evaluation and factory artifacts. This is the repo's already-documented fallback and avoids rebuilding a mature trainer. The current simulated quantization mode is useful pedagogically but is not acceptable evidence that an 8B packed-base QLoRA run fits.

### 7. Offline evaluation is primary; games are a necessary secondary gate

The main offline suite is deterministic and large enough for slice analysis:

- strict parse and legal-move rate;
- tactical positions with engine-validated solutions or equivalence tolerance;
- engine-relative centipawn loss with fixed nodes/depth, mate-aware conversion, and capped penalty;
- blunder rate at a frozen centipawn-loss threshold;
- opening/middlegame/endgame, score-state, check, promotion, castling, en-passant, tactical/quiet, and recovery slices.

Stockfish first evaluates the suite as the ruler calibration. Exact-move accuracy is not a headline metric because chess often has multiple sound moves.

Paired games then test compounding errors. Baseline and candidate play identical openings with colors reversed against the same pinned opponent. The smoke tier is deliberately small. The full tier records PGNs, timeouts, illegal losses, W/D/L, confidence interval, and color split. It is run only with operator approval.

### 8. Ship criteria are conjunctive

The candidate must clear legality/format, offline quality, paired games, breadth, and performance together. A chess win that damages general breadth becomes a routed-only candidate and still cannot ship unless its package and router constraints are explicit. A candidate with better centipawn loss but no game-score improvement is not declared successful.

The full before/after report uses the canonical factory schema. Failed runs remain report artifacts. Only a passing run creates `specialists/<id>/`.

## Risks / Trade-offs

- **[8B packed-base gradients remain unsupported in MLX-Swift]** → Run the bounded feasibility gate first; fall back to pinned `mlx_lm`; do not build more native surface until the primitive works.
- **[Fine-tuning teaches opening imitation but not play]** → Split by games and canonical positions, emphasize non-opening and recovery states, report phase slices, and require paired games.
- **[Engine labels collapse diversity to one line]** → Accept moves within a frozen engine-equivalence tolerance, sample among near-equal teacher moves where appropriate, and report entropy/duplicate-target diagnostics.
- **[Centipawn loss is unstable near mate or across engine settings]** → Pin engine nodes/depth and options, handle mate separately, cap penalties, and never compare results produced under different settings.
- **[A generated legal move is still strategically weak]** → Keep legality, tactics, centipawn loss, blunders, and games as separate gates.
- **[Match conclusions are noisy and expensive]** → Use paired openings and confidence intervals; use offline positions for iteration and reserve the full match for finalists.
- **[Dataset licensing is unclear]** → Block ingestion until license and redistribution/training use are recorded; publish only manifests or small fixtures unless source terms allow redistribution.
- **[Prompt/history format exceeds useful context or leaks labels]** → Measure token lengths, cap history consistently, keep test prompts free of demonstrations from test positions, and pin the chat template.
- **[Heavy work degrades the Mac host]** → Require approval per heavy phase, use the GPU lock, cap memory below host capacity, start with one bounded step, avoid sweeps, and terminate spawned processes.
- **[Chess specialization harms language breadth]** → Keep a frozen general-language regression gate and label any accepted artifact as routed-only with explicit non-chess exclusions.

## Migration Plan

1. Land only schemas, small fixtures, and no-GPU tests first.
2. Add the data/eval environment without changing existing CLI behavior.
3. Prove the evaluator against Stockfish and deterministic fixtures.
4. Freeze the exact model and baseline configuration.
5. With separate approval, run the packed-base feasibility and tiny-overfit gates.
6. With separate approval, run pilot training and evaluation; advance only if gates pass.
7. Assemble and validate the factory run. Package only on `ship`.

Rollback is file-level: remove the chess-specific scripts/fixtures/spec package. Existing factory commands and schemas remain unchanged. Large datasets, models, and runs stay outside Git in cache/ignored paths.

## Open Questions

- Select and approve the game corpus license and distribution policy before any download.
- Choose the pinned Stockfish node or depth budget after a tiny timing calibration; do not tune it after seeing candidate scores.
- Freeze pilot/full row counts and match-game counts after estimating wall time and storage on this Mac.
- Decide whether the first artifact is strictly a routed move policy or whether a later, separate capability should add natural-language chess explanation.
